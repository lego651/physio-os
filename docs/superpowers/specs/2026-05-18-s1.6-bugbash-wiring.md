## 1. Scope statement

S1.6 is a focused bug-bash and wiring sprint. It does not introduce new features — it closes the gaps left by S1.5 and makes the review engine ready for real patient sends.

### In scope

**Area A — Voice-to-review-table handoff (AC-B8 from S1.5):**

The `onComplete` prop on `VoiceIntakeChat` fires but `staff/intake/page.tsx` does not wire it. Clicking "Confirm & save" in the voice session saves the `intake_records` row but the therapist has no path to the review requests table. S1.6 wires this: Confirm navigates to `/dashboard/review-requests?prefill=<base64-json>` which opens the Add Row panel pre-filled with patient name and therapist name.

**Area B — Inline edit persistence (bug):**

`AdminReviewRequestsClient` holds `editPhone` and `editEmail` in local React state with no persistence path. There is no `PATCH /api/admin/review-requests/[id]` endpoint. Edits are lost on page refresh. Worse: the Send button uses `row.patient_phone` / `row.patient_email` from the loaded rows, not the local edit state — meaning a staff member can correct a phone number inline and still send to the old number. This is a silent data bug. S1.6 adds the PATCH endpoint and fixes the send flow to auto-persist edits before sending.

**Area C — AI prompt few-shot tuning (backlog 3.5, high priority):**

Current `buildReviewPrompt` has no examples. Drafts read as generic. Few-shot examples are the highest-leverage prompt improvement for draft naturalness and Google quality filter pass-rate. S1.6 adds 2 examples (RMT + acupuncture, the two primary V-Health services).

**Area D — Post-maps inline feedback (backlog 3.1, medium priority):**

After clicking "Open Google Maps," the patient sees nothing — no confirmation. S1.6 adds an inline message in `ReviewClient.tsx` after the maps button is clicked. One-line state change, no new route.

**Area E — Stage 0 operational checklist (non-code):**

Items 1.1 (unsubscribe test), 1.2 (opt-out rejection), 1.3 (Google Place ID) from s2-backlog are still open. S1.6 adds these to the operator runbook as a pre-prod checklist and confirms they are executed before `REVIEW_TEST_MODE` is flipped to false.

### D17-1 — AC-B8: URL param prefill, not cross-page state store

Voice session completes → "Add to review table" button in the DONE step of `VoiceIntakeChat` navigates to `/dashboard/review-requests?prefill=<base64-encoded-json>`. The payload is `{ patient_name, therapist_name }` only — phone and email are blank (front desk fills manually, per D16-2).

`AdminReviewRequestsClient` reads the `prefill` param via `useSearchParams()` on mount. If present: decode → set `showAddRow = true` → set `draft.patient_name` and `draft.therapist_name`. After first read, the param is not cleared from the URL (no `router.replace`) — the panel stays open if the user navigates within the page. If the user refreshes, the panel opens again with the same prefill, which is acceptable.

Navigation from `staff/intake/page.tsx` is handled by passing `onComplete` to `VoiceIntakeChat`:

```typescript
// staff/intake/page.tsx — passes onComplete to the client component
// The page itself remains a server component (auth guard runs server-side).
// useRouter lives inside VoiceIntakeChat (already a client component).
```

`VoiceIntakeChat` currently calls `onComplete?.(full)` after save succeeds (line 265 in voice-intake-chat.tsx). The `onComplete` prop now navigates. The router call goes inside `VoiceIntakeChat` itself — add `useRouter` there, or pass the navigation as a callback from the server page via a thin client wrapper.

Tech-lead decision: add a `navigateTo` prop to `VoiceIntakeChat` (string URL). On `onComplete`, call `router.push(navigateTo)` if provided. This avoids the server page needing to import `useRouter` (server components cannot use hooks). The server page passes the precomputed URL string: `/dashboard/review-requests?prefill=...`. The base64 encoding happens server-side before rendering.

Wait — the `patient_name` and `therapist_name` are not known at server render time (they come from the voice session at runtime). Therefore the URL cannot be precomputed server-side.

Revised approach: `VoiceIntakeChat` constructs the URL itself inside the `onComplete` handler. The component already has `useRouter` available (it is a client component). `staff/intake/page.tsx` passes no prop — `VoiceIntakeChat` handles the navigation internally after a successful save.

Final implementation (no new prop needed):

```typescript
// Inside confirmIntake() in VoiceIntakeChat, after successful save:
const prefill = btoa(JSON.stringify({
  patient_name: full.patient_name,
  therapist_name: full.therapist_name,
}))
router.push(`/dashboard/review-requests?prefill=${encodeURIComponent(prefill)}`)
onComplete?.(full) // still called for any external listener
```

`useRouter` is imported from `next/navigation` in `VoiceIntakeChat` (already a client component — no constraint violation).

The DONE step ("Session saved. Start another voice intake?") is not shown — navigation fires immediately after save. This is correct: the therapist's next action is always to add the patient to the review table.

### D17-2 — PATCH endpoint: contact fields only, no resend

`PATCH /api/admin/review-requests/[id]` accepts:

```typescript
{
  patient_phone?: string | null  // E164 or null
  patient_email?: string | null  // email format or null
}
```

- Validates: phone must match E164 regex if provided and non-null. Email must match email regex if provided and non-null.
- Auth: `requireAdminAuth()` — same as POST.
- DB: `UPDATE review_requests SET patient_phone = $phone, patient_email = $email WHERE id = $id`. Only the provided fields are updated (partial update — if only `patient_phone` is in the body, `patient_email` is not touched).
- Returns 200 with `{ id, patient_phone, patient_email }`.
- Returns 404 if no row with that id exists.
- Does NOT create funnel events. Does NOT trigger engine.send().

### D17-3 — Send flow: auto-persist inline edits before sending

`sendRow()` in `AdminReviewRequestsClient` checks whether `editPhone[row.id]` or `editEmail[row.id]` differ from `row.patient_phone` / `row.patient_email`. If they differ:

1. PATCH the row first (call `PATCH /api/admin/review-requests/${row.id}`).
2. If PATCH fails: show flash error, abort send. Do NOT send.
3. If PATCH succeeds: proceed to send (POST with `id: row.id`).
4. After send success: `loadRows()` — the table now shows the updated contacts.

Same logic applies in `bulkSend()`: for each row in the sendable list, check for pending edits and PATCH first if needed, then send.

No separate "Save contact" button per row. Auto-persist on Send is the only path.

### D17-4 — Few-shot prompt: 2 examples, English only

`buildReviewPrompt` receives the same inputs. The output changes to include 2 example blocks before the generation instruction.

Format:

```
Here are two examples of well-written reviews for similar clinics:

Example 1 (massage therapy):
"I've been dealing with chronic lower back pain for years and finally found lasting relief at this clinic. My RMT walked me through exactly what was causing the tension and gave me exercises to do at home. I left my first session feeling 10 years younger. Highly recommend for anyone who's tried everything else."

Example 2 (acupuncture):
"I was skeptical about acupuncture but my shoulder injury wasn't responding to anything else. After three sessions here I noticed real improvement — less stiffness in the morning and better range of motion. My TCM practitioner was patient with all my questions. I'll be coming back."

Now write a review for the patient below. Match the tone: specific, personal, no promotional language.
```

These examples are injected between the clinic context block and the generation instruction. They are not in `<notes>` tags — they are above the patient's notes to anchor tone before the patient's specific input is shown.

Rationale for these two examples: RMT and acupuncture account for the majority of V-Health sessions. Each example demonstrates: (1) a specific symptom mentioned, (2) an outcome stated in patient terms, (3) a recommendation without being promotional, (4) first-person. The therapist name is deliberately omitted from the examples to avoid the model copying the example therapist name instead of using the actual therapist from the prompt context.

No language detection or Chinese-language examples in S1.6. English-only for Phase 1.

### D17-5 — Post-maps feedback: inline state, no new route

`ReviewClient.tsx` tracks a `mapsCopied` boolean in local state (initialized `false`). When the "Open Google Maps" button/link is clicked:

```typescript
setMapsCopied(true)
// open the mapsHref in a new tab (window.open or href with target="_blank")
```

After click, render inline below the maps button:

```
Thanks — if you submitted your review, it may take a few minutes to appear publicly.
```

No API call. No navigation. No new route. The maps link remains visible and clickable (patient may want to click again if the tab didn't open).

Existing `maps_redirected` funnel event tracking is preserved — it fires via `POST /api/review-requests/track` on the button click.
