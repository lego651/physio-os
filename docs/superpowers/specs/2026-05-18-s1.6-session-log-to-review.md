## 1. Problem statement

The current system has two disconnected tables:

- `intake_records` — therapist voice logs (patient name, treatment area, therapist, notes). Saved on voice session confirm.
- `review_requests` — admin-managed list of patients to send review requests to. Currently populated manually via "+ Add row" in the dashboard.

The five rows visible at `/dashboard/review-requests` are all manually created test data. They carry no real session information. The therapist voice flow and the review request flow are completely separate — zero data flows between them.

S1.6 closes this gap. After S1.6 ships:

1. Every therapist voice session automatically produces a `review_requests` row (status=`pending`, contact=null).
2. The row carries `therapist_name`, `service_type` (massage / physio / acupuncture / chiropractor / other), and `patient_name` from the voice log.
3. The admin/front-desk sees real patient rows in the review table, adds phone/email, and sends.
4. The five existing test rows are deleted before ship.

## 2. Locked decisions D18-1 through D18-8

### D18-1 — Session type: AI-extracted from treatment step, no new voice step

The existing Step 2 of VoiceIntakeChat asks "What treatment did you do?" and uses Claude to extract `treatment_area` (e.g. "right shoulder"). The therapist's answer already contains service type information ("deep tissue massage on right shoulder", "acupuncture on lower back").

S1.6 changes the Step 2 Claude extraction to return two fields from the same audio, in one call:

```typescript
{ treatment_area: string, session_type: 'massage' | 'physio' | 'acupuncture' | 'chiropractor' | 'other' }
```

Classification rules embedded in the Claude prompt:
- Any mention of massage, RMT, deep tissue, Swedish, relaxation → `massage`
- Any mention of physio, physiotherapy, exercise, rehabilitation, stretching, mobility, strengthening → `physio`
- Any mention of acupuncture, TCM, needles, cupping → `acupuncture`
- Any mention of chiro, chiropractic, adjustment, manipulation → `chiropractor`
- Ambiguous or unrecognized → `other`

The voice flow stays at 4 steps. No new step is added.

The existing `extractSingleField()` function in `apps/web/lib/intake/extract.ts` is replaced with `extractTreatmentStep()` which returns the two-field object. The upload route step=2 branch is updated to call the new function.

### D18-2 — Auto-create review_requests on voice confirm

When the therapist clicks "Confirm & save" in VoiceIntakeChat, the save endpoint (`POST /api/intake/save`) creates two rows in the same server-side operation:

1. `intake_records` — the session log (unchanged behavior, plus new `session_type` field).
2. `review_requests` — a new row with `status='pending'`, `patient_phone=null`, `patient_email=null`, `therapist_name` from the session, `service_type` from the extracted session_type, `intake_record_id` FK to the intake_records row.

No manual "Convert" button. No second admin action required. The auto-create happens server-side in `POST /api/intake/save` using the service-role Supabase client (bypasses RLS).

If the `review_requests` INSERT fails, the `intake_records` row is still committed (non-atomic). A failed review_requests creation is logged as a server warning but does not fail the intake save response. The therapist is not blocked.

Rationale: the intake record is the source of truth. The review request is derived and can be recreated manually via "+ Add row" if the auto-create fails.

### D18-3 — One review_request per session, no same-day dedupe

Each voice session produces exactly one `review_requests` row. If a patient has two sessions in one day (e.g. massage then physio), they produce two rows — different `therapist_name`, different `service_type`, different review context.

The existing dedupe guard (409 on same clinic+name+email/phone) is not triggered because the auto-created rows have `phone=null` and `email=null`. No conflict with the existing guard.

### D18-4 — Migration 018: add session_type to intake_records

New migration `018_intake_session_type.sql`:

```sql
ALTER TABLE public.intake_records
  ADD COLUMN session_type text NOT NULL DEFAULT 'other'
  CHECK (session_type IN ('massage','physio','acupuncture','chiropractor','other'));
```

`review_requests.service_type` already exists as a `text` column (migration 016). No change to `review_requests` schema. S1.6 simply populates it from the voice extraction.

Migration 018 also adds `intake_record_id` FK to `review_requests`:

```sql
ALTER TABLE public.review_requests
  ADD COLUMN IF NOT EXISTS intake_record_id uuid REFERENCES public.intake_records(id) ON DELETE SET NULL;
```

This FK is nullable — existing review_requests rows (manual + auto-created before this migration) are valid with `intake_record_id=null`.

### D18-5 — Mock data cleanup: DELETE all existing rows

The 5 existing `review_requests` rows in prod (all `status=sent`, created during testing) are deleted before S1.6 ships. Deletion is done via Supabase service-role REST DELETE, the same pattern used in the May-17 DB clean session. The cascade delete from migration 017 removes their `review_funnel_events` rows automatically.

No `is_test` column. No migration required. Jason executes via Supabase dashboard SQL editor:

```sql
DELETE FROM public.review_requests;
```

(This is safe: after S1.6 ships, all rows come from real voice sessions. The table starts clean.)

### D18-6 — review_requests page: "pending" status, contact-fill workflow

After S1.6, newly auto-created rows appear in the review-requests table with:
- `status = 'pending'` (new status value — currently the table has 'queued', 'sent', 'failed')
- `patient_phone = null`, `patient_email = null`
- Channel badge = "Add contact" (existing behavior for missing contacts)

Front-desk workflow:
1. See new row from voice session (patient name, therapist, service type visible).
2. Type phone/email into the inline edit inputs.
3. Check consent checkbox.
4. Click Send — existing `sendRow()` flow handles from here.

The inline edit persistence bug (Item B in s1.7-bugbash-backlog.md) means edits are lost on refresh. This is a known gap, carried forward to S1.7. For S1.6: front-desk must fill contact and send in one session without refreshing. Acceptable for the pilot.

The `status` column must accept `'pending'` — check migration 016 CHECK constraint. If there is a CHECK constraint restricting status values, migration 018 must update it to include `'pending'`.

### D18-7 — Voice UX: show session_type in confirm screen

The CONFIRM step currently shows: Patient / Treatment / Therapist / Notes / Date.

S1.6 adds "Service" row showing the extracted session_type (e.g. "massage"). If extraction returns "other", display "Other — verify before sending review". The therapist can edit via the existing edit-bubble mechanic if wrong.

The `VoiceIntakeResult` interface gains a `session_type` field:

```typescript
export interface VoiceIntakeResult {
  patient_name: string
  treatment_area: string
  session_type: 'massage' | 'physio' | 'acupuncture' | 'chiropractor' | 'other'
  therapist_name: string
  session_notes: string
  date_of_visit: string
}
```

### D18-8 — Navigation after confirm: direct to review-requests with prefill

After voice confirm + save, `VoiceIntakeChat` navigates to `/dashboard/review-requests?prefill=<base64>`. This was already specified in the superseded D17-1. Carry forward unchanged:

- Payload: `{ patient_name, therapist_name, service_type }` (now includes `service_type`).
- `AdminReviewRequestsClient` reads `prefill` param via `useSearchParams()` on mount.
- Opens Add Row panel pre-filled — but since the row was auto-created (D18-2), the prefill is informational only (the row already exists). The Add Row panel should NOT be opened via prefill — instead, the table should scroll to / highlight the newly created row.

Revised navigation approach (replaces D17-1):

After save, the API response includes the new `review_requests.id`. The navigation URL becomes:

```
/dashboard/review-requests?highlight=<review_request_id>
```

`AdminReviewRequestsClient` reads `highlight` param on mount, scrolls to the matching row, applies a brief highlight style (yellow border, 3s fade). The Add Row panel is NOT opened. This is the correct UX — the row already exists, front-desk just needs to add contact info.

No `prefill` param in S1.6. The Add Row panel is still accessible via the "+ Add row" button for manual entries.

## 3. Data model

### Migration 018 (`018_intake_session_type.sql`)

```sql

  ADD COLUMN session_type text NOT NULL DEFAULT 'other'
  CHECK (session_type IN ('massage','physio','acupuncture','chiropractor','other'));

-- Add intake_record_id FK to review_requests
ALTER TABLE public.review_requests
  ADD COLUMN IF NOT EXISTS intake_record_id uuid
  REFERENCES public.intake_records(id) ON DELETE SET NULL;

-- Add 'pending' to review_requests status if there is a CHECK constraint
-- (check migration 016 — if status is unconstrained text, this is a no-op comment only)
-- ALTER TABLE public.review_requests DROP CONSTRAINT IF EXISTS review_requests_status_check;
-- ALTER TABLE public.review_requests ADD CONSTRAINT review_requests_status_check
--   CHECK (status IN ('pending','queued','sent','failed'));
```

Tech-lead must inspect migration 016 to confirm whether `status` has a CHECK constraint before finalizing migration 018.

### API: `POST /api/intake/save` — new behavior

Input (unchanged interface):

```typescript
{
  patient_name: string
  treatment_area: string
  session_type: 'massage' | 'physio' | 'acupuncture' | 'chiropractor' | 'other'
  therapist_name: string
  session_notes: string
  date_of_visit: string
  source: 'in_app' | 'telegram' | 'manual'
  raw_transcript: string | null
}
```

Server logic (new):

1. INSERT into `intake_records` (existing behavior + new `session_type` column).
2. INSERT into `review_requests`:
   - `clinic_id`: from intake (default 'vhealth' → resolve to UUID via clinics lookup or use the slug-based approach already in the codebase)
   - `patient_name`: from intake
   - `therapist_name`: from intake
   - `service_type`: from `session_type`
   - `intake_record_id`: the UUID returned from step 1
   - `status`: `'pending'`
   - `patient_phone`: null
   - `patient_email`: null
   - `channel`: `'email'` (default — front-desk will override if they have phone)
   - `consent_confirmed`: false (front-desk confirms per-send)
3. Return response:
   ```typescript
   { id: string, review_request_id: string }
   ```
   Where `id` is the `intake_records.id` and `review_request_id` is the new `review_requests.id`.

### API: `POST /api/intake/upload` (step=2) — new extraction output

Step 2 upload now calls `extractTreatmentStep()` instead of `extractSingleField()`.

Response shape changes from:
```typescript
{ transcript: string, field: string }
```
To:
```typescript
{ transcript: string, treatment_area: string, session_type: 'massage'|'physio'|'acupuncture'|'chiropractor'|'other' }
```

The client (`VoiceIntakeChat`) reads both fields and stores them in the `result` state.
