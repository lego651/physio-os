## 1. Scope statement

### In scope

S1.5 is a focused improvement sprint on top of the existing S2 review engine. It covers two areas:

**Area A — Review Requests table UX (4 sub-items):**

- A1. Compact one-row-per-entry table replacing the current send form + flat list
- A2. Clinic and Channel as global settings outside the table; smart channel routing per row
- A3. Per-row consent checkbox + individual send button
- A4. Bulk send button below table, sequential throttle (10 max, no queue infrastructure)

**Area B — WeChat-style voice intake for pre-filling review requests:**

- B1. 4-question step-by-step voice capture (one STT pass per question)
- B2. Whisper `/audio/transcriptions` endpoint, no locked language, physio hint injection
- B3. Claude extract forces English output for all structured fields
- B4. Chat bubble UX with per-answer edit (re-record or type); confirm card at end
- B5. Voice intake output pre-fills the review requests table (loose coupling — no `patients` table)

### Out of scope

- `patients` table and patients management UI — killed for S1.5. See section 6.
- Therapist admin CRUD page — deferred. See section 6.
- CASL consent gate reinstatement — founder-accepted risk for V-Health pilot. Non-negotiable before clinic #2. Not in this sprint.
- Bulk send queue/retry infrastructure (Redis, background workers) — explicitly killed for V-Health scale.
- Any change to the S2 review engine backend (engine.ts, adapters, token logic, funnel events) — S1.5 is UI + intake only.

## 2. Locked decisions D16-1 through D16-8

All 8 decisions were reached in the 2026-05-17 brainstorm session and confirmed by Jason ("k. 开始吧").

### D16-1 — Voice UX: per-question STT, not one-shot record-all

Each of the 4 questions gets its own STT pass. The therapist speaks one answer, taps stop, transcription fires immediately. Only then does the next question appear.

Rationale: per-question STT is more accurate. The transcript for one field is short and unambiguous (e.g. "John Smith" or "right knee massage"). A one-shot 60-second recording produces a longer transcript that Claude must parse, introducing extraction errors. Jason held firm against PM's preference to simplify.

### D16-2 (revised 2026-05-17) — No `patients` table. `review_requests` stays string-based.

`review_requests` stores `patient_name TEXT`, `patient_phone TEXT`, `patient_email TEXT` as plain strings. No FK to a `patients` table. Opt-out matching uses `phone + email` string lookup in `review_opt_outs`.

Voice intake only captures `patient_name`. Front-desk staff manually adds `phone` and `email` in the table row before sending — these fields are not collected during the voice session.

Original D16-2 (patients table with FK) is superseded by this revision. The patients table is killed entirely for S1.5.

Rationale: adding a `patients` table in this sprint creates a foreign-key dependency that blocks the voice-to-review pre-fill flow and introduces a consent model that is over-engineered for the V-Health pilot scale. The string-based model already in migration 016 is sufficient. Revisit patients table when volume or multi-clinic needs it.

### D16-3 — Consent model: per-send checkbox, logged in metadata

One consent checkbox per row in the table. Checked state is logged in `review_requests.metadata.consent_confirmed = true`. Engine already enforces `consent_confirmed` before dispatch (existing behavior in `POST /api/admin/review-requests`).

No `consent_at` timestamp column on a `patients` row — that design is superseded by D16-2 revision. Opt-out via `review_opt_outs` table (already in migration 016 via the `review_opt_outs` table; strings matched by clinic_id + contact + contact_type).

### D16-4 — Intake and review-requests are decoupled

`/staff/intake` → voice workflow → writes `intake_records`. Therapist's tool.

`/dashboard/review-requests` → table view → reads existing `review_requests` rows + `review_opt_outs` for greyed-out logic → sends via existing engine.

Voice intake does NOT auto-create a `review_requests` row. It produces a pre-fill payload that the user carries into the table manually (or via the "Add to table" action in the confirm card). Data flow is intentionally loose.

### D16-5 — Therapist field: dropdown from `therapists` table (existing data)

Migration 013 (seeded for V-Health) already has `therapists` rows. The voice intake step 3 uses a picker (not STT) for the therapist field — dropdown avoids transcription errors on names.

Admin CRUD page for the `therapists` dropdown is deferred. For V-Health pilot, the seed data is sufficient.

### D16-6 — Bulk send: sequential, no queue, 10 rows max

Bulk send iterates over checked rows with sequential `await` calls (or `Promise.allSettled` with a concurrency cap of 3 — implementation detail for tech-lead). No Redis, no retry queue, no background worker.

Jason's words: "不要搞那么复杂." Hard limit: 10 rows per bulk operation. If David Wang has more than 10 patients to send to at once, that is a Phase 2 problem.

### D16-7 — Voice duration 60s accepted. UX paradigm: WeChat-style chat

Each question/answer is a chat bubble pair. The user (therapist) bubble shows the transcribed text with an edit pencil icon. Tapping edit allows re-recording or manual text correction. A confirm step at the end shows a preview card.

Canonical UX flow (must be implemented exactly as described):

```
[AI bubble]   What's the patient's name?
[User bubble] 🎤 → "John Smith"  [edit pencil]

[AI bubble]   What treatment did you do?
[User bubble] 🎤 → "right knee massage"  [edit pencil]

[AI bubble]   Which therapist?
[Picker]      [Jimmy ▼]

[AI bubble]   Session notes?
[User bubble] 🎤 → "patient reported less pain"  [edit pencil]

[AI bubble]   Here's what I got. Confirm?
[Preview card]
  Patient:   John Smith
  Treatment: right knee massage
  Therapist: Jimmy
  Notes:     patient reported less pain
  Date/time: 2026-05-17 auto-filled
[Confirm]  [Edit any]
```

Step 3 (therapist) uses a dropdown picker, not voice, because transcription errors on names cause wrong therapist assignment.

Date/time is auto-filled from `new Date()` at the moment the user taps Confirm — not asked during the voice session.

### D16-8 (new, 2026-05-17) — Whisper `/audio/transcriptions`, no locked language, physio hint

Use OpenAI Whisper `/audio/transcriptions` endpoint (not `/audio/translations`). Do not pass a `language` parameter — let Whisper detect automatically. This handles bilingual therapists (English + Mandarin) without forcing a language choice.

Pass a `prompt` field to Whisper with physiotherapy terminology hints:

```
Physiotherapy session note. Terms may include: RMT, OMT, TCM, acupuncture, massage therapy,
osteopathic, cervical, lumbar, rotator cuff, fascia, trigger point, IASTM, cupping.
```

Claude extract prompt must include an explicit instruction: "Output all fields in English regardless of the input language." This ensures the `intake_records` schema stays English-only even if the therapist spoke in Mandarin.

UI: display a non-mandatory prompt on the voice recording screen — "Please speak in English for best accuracy" (English only, not translated). This is a soft suggestion, not a gate.

Existing `whisper.ts` currently passes `language: 'en'` — this must be removed (D16-8).

## 3. Data model changes

### 3.1 No new tables in S1.5

S1.5 does not add any new migrations. All existing tables are sufficient:

| Table                        | Used for                                                            | Status                                    |
| ---------------------------- | ------------------------------------------------------------------- | ----------------------------------------- |
| `review_requests` (016)      | Stores string patient_name/phone/email + channel + consent metadata | Already exists, no change                 |
| `review_opt_outs` (016)      | Opt-out matching by clinic_id + contact string + contact_type       | Already exists, no change                 |
| `review_funnel_events` (017) | Funnel tracking per send                                            | Already exists, no change                 |
| `intake_records` (012)       | Voice intake session records                                        | Already exists, no change                 |
| `therapists`                 | Dropdown data for step 3 of voice intake                            | Already seeded via migration 013          |
| `clinics`                    | Global clinic config (name, channel default)                        | Already exists, already has `vhealth` row |

### 3.2 `review_requests` string fields (confirmation, no change needed)

Current schema (migration 016):

```
patient_name   TEXT NOT NULL
patient_email  TEXT            -- nullable, SMS-only
patient_phone  TEXT            -- nullable, email-only
channel        TEXT NOT NULL CHECK (channel IN ('email','sms','both'))
metadata       JSONB           -- consent_confirmed logged here
```

This matches D16-2. No migration needed. Front desk fills `patient_phone` and `patient_email` manually in the table UI before sending.

### 3.3 Voice intake output schema (no DB change, just UX plumbing)

The voice session produces a pre-fill object:

```typescript
type VoiceIntakeResult = {
  patient_name: string // from step 1 (voice → Whisper → returned as-is)
  treatment_area: string // from step 2 (voice → Whisper → Claude extract → English)
  therapist_name: string // from step 3 (dropdown picker, not voice)
  session_notes: string // from step 4 (voice → Whisper → Claude extract → English)
  date_of_visit: string // auto-filled at Confirm tap (YYYY-MM-DD)
}
```

This object is written to `intake_records` on Confirm, AND can be used to pre-fill a new row in the review requests table. The two writes are independent.

## 4. Voice intake flow

### 4.1 Pipeline per voice step

```
[Therapist taps mic button]
        │
        ▼
MediaRecorder (webm/opus, max 60s)
        │
        ▼
POST /api/intake/upload  ← audio blob
        │
        ▼
whisper.ts — transcribeAudio(buffer, filename)
  - calls OpenAI /audio/transcriptions (whisper-1)
  - NO language param (D16-8)
  - passes prompt with physio terminology hints (D16-8)
        │
        ▼
For steps 2 and 4 only:
extract.ts — extractIntakeFields(transcript)
  - Claude Sonnet 4.5 via @ai-sdk/anthropic
  - Output.object({ schema }) — structured extraction
  - Prompt includes: "Output all fields in English regardless of input language" (D16-8)
  - Returns { fields, warnings }

For step 1 (patient_name):
  - transcript returned directly, no Claude extract
  - patient_name = transcript.trim()
        │
        ▼
[User bubble rendered with transcribed text]
[Edit pencil: re-record or type]
        │
        ▼ (after all 4 steps)
[Confirm card — preview of all fields]
[Confirm] → write intake_records row → optionally pre-fill review request row
```

### 4.2 API changes to `/api/intake/upload`

The upload route needs a `step` parameter to control whether Claude extract runs:

```typescript
// POST /api/intake/upload
// Body: FormData { audio: Blob, step: '1' | '2' | '3-picker' | '4' }
// step 1 → Whisper only, return { transcript }
// step 2 → Whisper + Claude extract treatment_area field only, return { field: string, transcript }
// step 4 → Whisper + Claude extract session_notes field only, return { field: string, transcript }
// step 3 → no audio, handled client-side by picker; no API call needed
```

This avoids running the full 5-field extraction on a single-sentence answer.

### 4.3 Whisper change required (D16-8)

Current `whisper.ts` line 36:

```typescript
providerOptions: {
  openai: { language: 'en' },
},
```

Must change to:

```typescript
providerOptions: {
  openai: {
    prompt:
      'Physiotherapy session note. Terms may include: RMT, OMT, TCM, acupuncture, ' +
      'massage therapy, osteopathic, cervical, lumbar, rotator cuff, fascia, ' +
      'trigger point, IASTM, cupping.',
  },
},
```

`language` is removed entirely. `prompt` is added.

### 4.4 Claude extract change required (D16-8)

Current `extract.ts` prompt does not contain a language instruction. Add to the Rules block:

```
- All output fields must be written in English, even if the transcript is in another language.
  Translate naturally; do not transliterate.
```

### 4.5 New component: `VoiceIntakeChat`

Location: `apps/web/app/staff/intake/voice-intake-chat.tsx`

This is a client component. It replaces (or wraps alongside) the existing `IntakeForm`. The existing `IntakeForm` stays as a fallback manual entry path.

State machine (4 steps + confirm):

```
IDLE → STEP_1_NAME → STEP_2_TREATMENT → STEP_3_THERAPIST → STEP_4_NOTES → CONFIRM → DONE
```

Each step renders:

1. An AI bubble with the question text
2. For voice steps (1, 2, 4): a mic button (tap to record, tap to stop); on stop, POST to `/api/intake/upload?step=N`; renders user bubble with result + edit pencil
3. For step 3: dropdown picker from therapists API; renders as a picker card then user bubble with selection + edit pencil
4. Edit pencil: opens inline text input pre-populated with current value (re-record button also available for voice steps)

Confirm card shows all 4 fields + auto-filled date. Two buttons: "Confirm" (writes intake_records + emits pre-fill event) and "Edit any" (returns to step 1 with current values preserved).

Non-mandatory language hint displayed above the mic button on each voice step:

```
Please speak in English for best accuracy.
```

## 6. Out of scope / deferred items

### `patients` table — killed for S1.5

Original D16-2 proposed a `patients(id, clinic_id, name, phone, email, consent_at, opted_out_at)` table with FKs from `review_requests` and `intake_records`. This is superseded by the D16-2 revision confirmed 2026-05-17.

The patients table adds migration complexity and a consent model that is not needed for the V-Health pilot at its current scale (David Wang manually enters patient contact details one by one). Revisit when:

- Volume requires deduplication (same patient, multiple visits)
- Multi-clinic expansion requires per-clinic patient rosters
- CASL reinstatement for clinic #2 requires a proper consent audit trail on the patient entity

At that point, a migration can add `patients` and backfill from `review_requests` string fields.

### Patients management UI — deferred

`/dashboard/patients` list/search view. Not built in S1.5. No patients table = no patients page.

### Therapist admin CRUD — deferred

An admin page for managing the `therapists` dropdown. Not in S1.5. V-Health pilot uses the seeded data from migration 013. If David Wang needs to add/remove therapists, it is a direct SQL update for now. Track as a backlog item.

### `service_types` admin-manageable — deferred

Currently hard-coded. Review after V-Health pilot shows whether field variation matters.

### Bulk send > 10 rows, queue/retry infrastructure — killed for V1

V-Health operates at <10 review sends per day at current volume. Redis queue is not justified. Revisit at 50+ clinics.

### CASL consent gate reinstatement — deferred (non-negotiable gate for clinic #2)

The S1.5 per-row consent checkbox is the pilot UX only. Before any second clinic goes live, the engine-level `consent_confirmed` gate must be enforced server-side (currently a metadata field, not a hard DB constraint). This is documented in D08 and must be surfaced at the June 5 ELT review.
